# 研报助手

自动生成《场外衍生品投资策略》一页通的桌面应用，供券商内部使用。

输入一句话需求，输出一份单页图文成品。全程使用真实数据，成文中每个数字均可回溯至来源；
需要交付时可同时导出 PDF，需要产品落点时可选调用 OptionHelper 完成推荐、定价与回测。

若需求中明确写出证券代码（如 `512000.SH`），系统会从原文直接提取并按受控工具目录/数据源
校验；该代码优先于 LLM 候选和板块默认映射。ETF 交易简称与基金官方全称会按同一工具别名核对，
代码无法验证时会明确停止，不会静默换成另一只 ETF。

> 一页通指单页图文密排的研究成品，非多页 Word 长报告。版式对标 0720 三份模板
> （券商板块 / AI 产业趋势 / 长鑫科技 IPO）。

---

## 生成流程

```
                          一句话需求
                               │
                               ▼
   ① 需求解析    识别研究主题、事件、研究篮子与触发实体（若事件由具体公司引发）；
                 对需求中的市场判断做数据查证
                 未点名 ETF 的产品诉求须先由分析师确认候选 ETF
                               │
                               ▼
   ② 摸底取数    按论点库全部判定所需字段取数；行情类字段取确认 ETF 自身序列；
                 估值/盈利类字段按其跟踪指数真实成分股整体法聚合。ETF 成分
                 无法核验时宁可留缺口，绝不以宽泛行业或代表个股替代
                               │
                               ▼
   ③ 触发判定    114 条论点逐条判定，得出本次被真实数据触发的论点；
                 研报观点中可转译为条件-验证结构的，自动升级为同等地位的候选
                               │
              ┌────────────────┴────────────────┐
              ▼                                 ▼
      数据触发的候选                     研报提炼的候选
      63 条判定，阈值机械判定            sources/ 内 PDF，
                                         逐字原文 + 表格原文，
                                         机械校验（仅 --pick）
              │                                 │
              └────────────────┬────────────────┘
                               ▼
   ④ 主轴选取    两类候选统一编号，选 2~3 条、尽量跨类别
                 默认自动选取；--pick 时由分析师勾选
                               │
                               ▼
   ⑤ 人工补数    可选加载 --overrides；只补 writer 所需的非判定字段，
                 禁止用手填值触发机械论点
                               │
                               ▼
   ⑥ 论述生成    只使用已取到的真实数据；数据与论点矛盾时须指出该逻辑不成立
                               │
                               ▼
   ⑦ 数字溯源    成文中每个数字逐个回指真值，对不上标记为可疑
                               │
                               ▼
   ⑧ 排版渲染    只为同口径时间序列生成趋势图；其他指标改为数据卡或不配图；
                 输出一页通 HTML；可选 PDF；可选调用 OptionHelper
                               │
                               ▼
                 一页通成品 + 内部底稿 +（可选）产品报告
```

**关键在于第 ③ ④ 步**：报告论证什么由本次的真实数据决定，而非由固定模板决定。
更换标的或时点，成立的论点组合随之改变，报告视角亦随之改变。

两条候选通道的可证伪性来源不同：数据触发靠阈值机械判定，可自动选用；
研报提炼靠分析师点开原文核对，因此**只在 `--pick` 模式下出现，不能自动选取**——
但其中描述"某标的达到某情形时另一标的历史表现"的事实性观点，会被自动转译为
历史回测结构并验证，验证通过后即以机器判定的身份进入自动候选（详见 `DESIGN.md` §7.6）。

## 运行方式

### 主路径：给定一句话需求

```bash
python main.py -b "昨晚SK海力士发了业绩，芯片板块最近明显回调，有无相关板块建议？"
```

系统解析出主题、事件、涉及板块、代表标的及触发实体（若事件由具体公司引发），
并对需求中的市场判断（如"最近明显回调"）以真实数据查证，返回支持或不支持的结论。

### 研究主题、研究篮子与挂钩 ETF

三者必须分开：**研究主题**回答“研究什么”（例如光模块/光通信）；**研究篮子**是经核验的
相关公司或 ETF 实际成分股，用于基本面、估值等整体法数据；**挂钩 ETF**是正式报价使用的可交易
工具，其自身行情、波动率和流动性单独计算。内部如需个股锚点，仅供取数或校验，默认不写入客户正文。

用户未在需求中明确 ETF 代码而提出“推荐产品”时，系统不会自行静默选定 ETF：会展示人工维护池与
iFinD 动态发现的候选、主题匹配理由和近 20 日流动性，要求分析师确认或输入代码。动态发现不是让 LLM
猜基金代码：需求解析器只生成有限的检索主题及同义词（例如“汽车电子”扩展为“智能驾驶、智能汽车、
车联网”），系统再查 iFinD 全市场基金目录并核验官方简称、跟踪指数、主题暴露与流动性。因此
`516520.SH` 等不在常用池中的 ETF 也能成为本次候选；通过校验后只在当前运行临时使用。
主题 ETF 流动性采用分级展示：近 20 日日均成交额达到 1 亿元为“优选”，0.3–1 亿元为“谨慎可选”并
要求正式询价前结合名义本金复核冲击成本，低于 0.3 亿元才硬性拒绝。手工输入的沪市 `.SS`、`.XSHG`
后缀会自动规范为 iFinD 使用的 `.SH`，深市 `.XSHE` 规范为 `.SZ`。

确认页提供两条取数路径：有可靠标准行业时可按“标准行业/人工主题篮子”研究；跨行业细分主题找到了
合适 ETF 时，可选“主题 ETF 路径”，直接以该 ETF 的真实跟踪指数成分作为研究篮子，不再要求分析师
猜一个标准行业。若真实成分篮子不可取得，基本面/估值字段会明确留为缺口，绝不退回宽泛行业或单只
“代表股”冒充。

### 辅路径：扫描市场推荐选题

```bash
python main.py
```

先输出候选主题清单，再按序号生成，支持多选：

```bash
python main.py 1 4
```

成品输出至 `output/`。每份一页通同时并排产出一份 `*_内部底稿.md`，
记录本次分析对象与口径、ETF 自身行情分析与挂钩选择路径、哪些字段未取到及其原因、
需求中提到但数据源不提供的外部事实、撰写环节漏写的逻辑、校验器标出的可疑数字，
以及本次引用的研报出处。板块映射或用户点名的 ETF 会展示自身行情指标及流动性复核；
候选择优路径还会保留完整候选池、入选标记和实测指标，供分析师复核。
该文件仅供内部使用，不随一页通对外发出。

一页通 HTML 在屏幕打开时会把符合图表规范的同字段时间序列、同量纲比较和同一篮子散点图
呈现为可缩放、可悬停查看的本地 ECharts 图；导出 PDF 或打印时，自动切换为**同一份数据**生成的
静态图，以保持离线、单页和可审计。运行文件随项目保存在 `assets/vendor/echarts.min.js`；若报告被
单独复制而未带该文件，HTML 会保留静态图，不会出现空白图表位。

研究完成后还会额外生成 `*_内部交互复核.html`，用于分析师更集中地查看已验证的主题篮子、成分股
估值—盈利分布、历史序列和（仅在择优路径存在时）ETF 候选比较。它不重新取数或调用 LLM。首次使用
内部复核页需在**运行 GUI 的同一 Python 环境**安装：

```powershell
python -m pip install pyecharts
```

### 人工选取论证角度：`--pick`

```bash
python main.py -b "券商板块最近怎么样，有没有配置价值？" --pick
```

默认由系统从触发结果中自动选取 2~3 条。加 `--pick` 后，系统先完成摸底取数与触发判定，
将本次被真实数据触发的论点按类别分组输出（含方向与实测依据），由分析师输入序号勾选，
系统仅负责将选中的论点组织成文。

```
── 数据触发（行情数据阈值判定）──────────────
【盈利/基本面类】
   1. E1   盈利改善　[看涨]
      依据：归母净利同比 +16.67%
【资金/筹码类】
   4. F1b  资金逆势流出　[看跌]
      依据：区间+1.47%、资金-99.20亿

── 研报提炼（需核对原文后再选）────────────────
【供需/产业格局类】
  33. 英伟达与海力士签署合计约 USD 500bn 多边协议，被市场认为循环融资　[看跌]
      华泰证券《SK海力士：短期情绪错杀 长期版图重塑》2026-08-02 p1 · 4天前
      原文：近期英伟达与海力士及 SK 集团分别签署合计约 USD 500bn 的多边协议…
...
请勾选作正文主轴的序号（空格分隔，建议 2~3 条）
  > 1 4 33
```

两类候选统一编号、混合选取。直接回车则交回系统自动选取。

若选中的论点方向相反，正文如实呈现分歧；若方向全部一致，系统提示"报告不会呈现分歧"。
卖方研报系统性偏多头，而本产品的主要风险是看漏下行风险，故将方向集中度显式提示，
但不作阻拦。

### 人工补充非判定数据：`--overrides`

每份内部底稿会按本次实际缺口生成一段可复制的 JSON 模板。填写后重跑：

```bash
python main.py -b "SK海力士业绩对芯片板块有什么影响？" --overrides overrides.json
```

覆盖文件支持三类内容：schema 中允许人工补充的字段、需求解析出的外部事实，以及事件驱动
报告的“事件事实 + 传导关系”证据。它不是“上传一份研报”的替代品：它适合录入一项明确的、
自动数据源未覆盖的**展示/解释性事实**（例如带来源的行业经营指标、公司公开指引），供报告正文和
内部底稿引用。每个字段都必须填写来源，成品与底稿会标记为“人工填写”。系统会拒绝覆盖判定引擎
依赖的字段——人工数据不能伪装成机械取数结果去触发或改变一条论点。

研究逻辑的选择与“人工数据补充”无关。每次 GUI 研究都会先用自动行情触发论点库，再从 `sources/`
材料提炼带原文出处的候选；两类候选在同一张“选择本次报告逻辑”卡中展示，均须由分析师勾选后才
进入正文。选择“采用系统建议”只按证据质量和结构给出建议组合，不替代分析师判断；也可明确交回
系统自动挑选。

对于“某公司业绩/公告如何影响某个板块或 ETF”这类需求，后两项是**报告生成门槛**：缺少
至少一条带来源的事件事实，或缺少至少一条带来源的产业链传导关系，系统会明确显示“未生成
报告”，并停止在取数前；不会用板块行情代替事件分析，也不会调用 OptionHelper。该栏平时可留空；
只有实际识别为事件型需求时才会触发此门槛。GUI 会弹出“缺少事件传导证据”的提示，可直接打开
“管理事件证据”从已上传材料导入，或在 JSON 中使用：

```json
{
  "事件证据": {
    "事件事实": [{"内容": "已披露的业绩实际值或指引", "来源": "公司 IR 公告 p4"}],
    "传导关系": [{"关系": "供应链", "内容": "该事实如何影响本次 A 股行业或 ETF", "来源": "产业链研报 p8"}]
  }
}
```

官方 IR/交易所披露、带页码的已上传研报、或其他可核验材料都可作为来源；研报不再是唯一入口。
桌面端先把“上传补充材料”复制到项目 `sources/`；“管理事件证据 → 从已上传材料导入原文”可直接
选择这些 PDF，也支持选择本地 PDF/TXT/MD/DOCX，或由分析师手动输入 HTTPS 的**原始文件直链**。
系统只抽取并保留带文件名/页码的逐字片段，绝不调用 LLM
概括材料、自动认定事实或推断传导关系；分析师必须选中片段并明确导入为“事件事实”或指定关系
类型的“传导证据”。直链不抓取普通网页，下载件仅保存在被 Git 忽略的 `output/materials/` 供复核。

### 导出 PDF：`--pdf`

```bash
python main.py -b "券商板块最近怎么样？" --pdf
```

默认只生成 HTML；`--pdf` 使用 QtWebEngine 导出同名 PDF，并以真实页数执行正式交付校验。
PDF 实测为 1 页才可作为正式一页通交付；超过 1 页会在运行状态、桌面端和内部底稿明确标为
“不通过、禁止正式交付”，并定位首张 A4 后溢出的区块、列出优先压缩的图表/正文方向。未使用 `--pdf` 的 HTML 明确标为
“未校验的内部草稿”。内部底稿的版面预算仍只是预警，真实 PDF 页数才是最终依据。

### 调用 OptionHelper：`--optionhelper`

```bash
python main.py -b "酒ETF估值如何，有没有配置价值？" --optionhelper quote
python main.py -b "酒ETF估值如何，有没有配置价值？" --optionhelper quote --pdf
python main.py -b "酒ETF估值如何，有没有配置价值？" --horizon 6个月 --max-loss 20% --principal-fluctuation yes --return-preference "更偏上涨参与" --optionhelper quote
```

一页通只接入最新版 Skill 的 `recommend` 与 `quote` 受控链路。Research Helper 先把本次已验证的市场事实与
市场展望交接给 OptionHelper；OptionHelper Recommender 按指南完成 Intent / Research /
Critic，形成候选。分析师只确认主候选、改选备选或退回修改客户约束，**不填写产品编号或推荐理由**；
确认后的**本次**产品选择才写入一次性 `.optionhelper/selection.pending.json`。Research Helper 不在
观点包中建议产品或结构；OptionHelper 负责合同冻结、取数、收益结构、定价、Reporter 与
Designer。调用成功时，研报助手只读取同一次 ReportRun 的 `designer-input.json`，在一页通
最下方生成随本次结果变化的“推荐结构 · 参考报价”表；不会解析 HTML，也不会自行补价格。
调用失败时，失败阶段和原因写入内部底稿，研究报告仍照常交付。

观点包的固定边界是：`标的与选择原因`、`整体方向与历史波动率`、带来源和截止日的已验证
市场事实，以及`市场展望`（预期方向、观察窗口、支持因素、制约因素、待验证风险）。它不包含
产品名、结构、执行价、障碍或收益承诺。成品中的“挂钩标的”卡片只保留标的核心状态与一句话
选取原因，不重复正文的市场情况。

`selection.pending.json` 使用最新版公开选择字段，例如：

```json
{
  "selection": {
    "product_id": "已由 Agent 核验的产品编号",
    "underlyings": ["510300.SH"],
    "reason": "与已确认市场情景及客户约束匹配的理由",
    "suitable_for": [],
    "not_suitable_for": [],
    "main_risks": []
  }
}
```

若需要同一标的多行结构/参数报价，可由 Agent 额外提供新版协议支持的 `quote_variants`。
客户在初始需求中明确的期限、最大损失、本金风险偏好应写入 `constraints`；例如
`{"constraints": {"horizon": "6个月", "max_loss": "20%", "principal_fluctuation": true}}`。
未填写时，Research Helper 会显式传入项目默认档案（3个月、最大损失100%、接受本金波动）；
可在 `config.local.json` 的 `OPTIONHELPER_DEFAULT_CONSTRAINTS` 修改。客户本次输入优先于默认档案。
执行价等已确认合同覆盖可与 `selection` 并列写入 `term_overrides`；例如
`{"term_overrides": {"T": 0.5}}` 代表 6 个月。桥接层不自行估计价格或障碍。

`selection.pending.json` 是**一次性待报价件**，不是可跨运行复用的项目设置。Quote 开始时，桥接层
以当前 `run_id` 原子地把它移到 `.optionhelper/selections/active/<run_id>.json`，先硬校验
`selection.underlyings` 与本页挂钩标的一致；报价无论成功、业务拒绝还是配置失败，都会归档到
`.optionhelper/selections/archive/<run_id>.json` 并写入 `lifecycle.state=consumed`。归档只供审计，
绝不再作为任何运行的输入；旧 `.optionhelper/selection.json` 也不再读取。下一次报价必须重新写入
一份 pending selection，因而不会拿上一轮的 ETF、市场方向或产品选择生成新报告的价格。

桥接层只从 pending selection 保留产品选择、理由及客户条件；`underlying`、`market_view`、
`output_type=quote` 与 `format=html` 始终由**本次观点包/调用**强制写入，不能由旧文件覆盖。
命令行也可直接输入本次客户条件：`--horizon`、`--max-loss`、`--principal-fluctuation yes|no`
与可选的 `--return-preference`。前三项以受控字段传给正式报价；收益偏好作为客户原话单独
传达给 OptionHelper，不由 Research Helper 翻译成产品建议。

需求中点名的 Call Spread、鲨鱼鳍等结构或报价诉求，也会从原文提取为独立的“客户产品诉求”：
不进入研究标题、研究关注点、论点规划或市场观点包；仅在正式报价时连同客户条件交给
OptionHelper，并标明须经其 Recommender 与合规校验，不能被当作 Research Helper 的结构建议。

### 运行进度与可追踪日志

每次命令都会先显示唯一 `run_id`，并在终端按阶段展示状态和耗时：需求解析 → 市场数据与
研究底稿 → 研究观点 → 数字校验 → 报告与底稿 →（可选）正式报价 →（可选）PDF。DeepSeek
请求发出后会即时显示“正在等待”，并每 15 秒报告已等待时长，避免长响应看起来像卡住。运行结束后
打印总耗时、输出路径、分析标的/数据口径和下一步建议。AkShare 内部的无害 pandas 切片警告会被
屏蔽；项目自己的告警与错误仍正常显示。

完整记录保存在被 Git 忽略的 `output/runs/<run_id>.json`，逐事件日志保存在同名 `.jsonl`：
其中包括每个阶段、DeepSeek 调用的尝试次数/耗时、OptionHelper 就绪检查与正式报价耗时、
交付文件和失败恢复建议；不会记录 API Key、请求头或完整外部响应。DeepSeek 仅对已识别的
瞬时网络/服务端/空响应错误作有限退避重试；额度截断、认证及参数错误不会盲目重试。

正式报价是独立的可降级阶段：报价开始前研究报告会先写入最终 HTML；报价成功后会以**报价后的最终
HTML**重建内部底稿与 PDF，并重新实测页数，避免出现“页底已有报价、底稿仍写未调用”的状态。重建或
一页校验失败时，不得沿用报价前 PDF 作为正式交付。报价失败则保留研究报告并交付内部底稿，同时在
终端、底稿及运行摘要中保留失败阶段与操作建议。统一就绪检查只验证 Refresh Token 已保存和依赖/Store 已就绪；正式报价
阶段才会向 iFind 交换短期 Access Token。若此处返回“iFind 鉴权失败”，表示保存的 Refresh
Token 已失效、被撤销或无权使用；它既不是研究层 iFinD 账号密码失败，也不是行情额度不足。
报告会保留，需按下方配置方式重新保存 Token 后再重试报价。
对于每日观察结构的日历绑定失败，系统只提示“重新审阅并选择无需每日观察的候选”或等待
OptionHelper 修复后重试，绝不自行换结构。

图表不是装饰：折线图只接受标签可验证为连续时间点、单位一致且有先后顺序的序列。PB 历史分位、
归母净利同比、区间涨跌幅等不同口径的单点指标，不会再被连成“走势”；系统会降级为数据卡、柱状比较
或不配图，并在内部底稿记录图表降级原因。

```bash
python -m core.docs
```

```
● [供需/产业格局类] 2026年资本支出将超过40万亿韩元，加速扩产　（看涨）
    华创证券《SK海力士…FY2026Q2业绩点评》2026-08-02 p3 · 4天前
    原文：由于生产计划加快和投资规模扩大，预计 2026 年的资本支出将超过 40 万亿韩元。
```

每条候选均附逐字原文、页码、出处与时效，可据此核对至研报原句。

**模型只做抽取，不做生成。** 观点必须是研报中明确表达的，且观点中的每个数字都要能在
所附原文中找到。校验按数值比对，机械执行，不依赖模型自觉；改写、杜撰、数值漂移均被拦下。

数字取自表格时，模型须另行逐字引出所读的表头行与数据行（`表格原文`）。该段同样逐字回查
文档，改写即整条作废——由此"数字 → 所引表格行 → 文档"的链条保持完整，而不是放宽成
"数字在文档某处出现即可"。

**事实陈述型观点可自动升级为机器验证论点。** 若某条观点明确写出两个标的各自的涨跌方向
（如"半导体跌15%的同时消费板块涨8%"），系统会将其转译为历史规律验证的输入：核对条件
标的当前是否处于该情形，再回测历史上观察标的是否稳定同向或反向表现。通过样本量、胜率、
样本外一致性三道闸的，自动进入数据触发候选，不再需要人工勾选后原样引用；未通过的不影响
原始观点仍留在候选清单中。

> **`sources/` 是工作台，不是资料库。** 研报时效性短，季度业绩点评过一个季度即基本失效。
> 建议每次生成前放入当次所需的研报，生成后清空。超过 90 天的会被标注内容可能失效。
> 引用的出处会固化进成品，原 PDF 删除不影响报告的可追溯性。
>
> `references/` 存放的是对标用的成品模板（0720 三份一页通），不参与生成。

## 论点库

`THESIS_LIBRARY.md` 是一份人工维护的 Markdown 表格，**114 条论点、9 大类**。
每条论点定义一种可复用的论证方式：

| 列 | 作用 | 例（V1 估值历史低分位）|
|---|---|---|
| 触发条件 | 何种情况下该条成立 | PE/PB 分位 < 30% |
| 所需数据 | 判定所依赖的数据 | PB/PE 及历史分位 |
| 市场状态特征 | 该条成立意味着什么 | 方向=看涨；价格位置=低位；确定性=高 |

九大类：估值、盈利/基本面、供需/产业格局、资金/筹码、情绪/交易、事件/催化、
宏观/流动性、扩散/映射、轮动/相对强弱。

> 情绪/交易类与衍生品关联最紧：波动率既是期权定价的核心输入，
> 也是"高波动对应高票息"一类论证的直接依据。

**多空对称**：每条方向性论点都有对称面，阈值亦对称（低分位 <30% ↔ 高分位 >70%）。
看跌论点的用途不是劝退客户，而是：①导向看跌方向的结构；②约束结构参数
（估值处高位则敲入线宜更低）；③支撑合规风险提示。

**扩充论点只需修改该 Markdown，不改代码**，但只有注册了判定函数的论点才会被触发。
当前已接判定 63 条——这是观点多样性的实际上限。

## 数据可信性保障

市场分析的本质是"真实数字 + 对数字的解读"。数字不可信则整份报告不可信。
全流程据此划分职责：

| 环节 | 职责 | 限制 |
|---|---|---|
| 规划 | 选取论证角度 | 不接触任何数字 |
| 取数 | 查取真实数据，并预先格式化为最终可读形式 | — |
| 撰写 | 只使用已取到的真实数据 | 不做任何换算，照抄格式化值 |
| 校验 | 逐个数字回指来源 | — |

**① 缺数据则留白，不填充。**
数据只有两种状态：真实取到的，或明确标注"数据待补"。未配置密钥时直接报错，
不以假数据替代。

**② 数值前置格式化。**
曾出现将 41.50 亿写成 414.98 亿（元至亿换算错位）。根因是让模型执行了换算。
现于取数环节即格式化为 `41.50亿元` / `1.46倍` / `2.48%`，撰写环节只照抄。
资金流向另将"净流入 / 净流出"写入文字——方向写反在投研中是致命错误。

**③ 证伪义务。**
论点是待检验的假设，不是既定结论。若真实数据与论点相悖——论点称"估值处历史低分位"
而实测 PB 22.56 倍，或称"分红改善"而现金分红为 0——必须如实指出该逻辑不成立，
不得圆场。

> 该防线针对的是比"数字错"更隐蔽的一类错误：**数字全对，论断却是假的**。
> 曾有一份成品 8 个数字全部溯源通过，正文却写着"估值处于历史低分位"。

**④ 逐个数字溯源。**
成文中每个带单位的数字都要能回指到一个真实取到的值，对不上则标记为可疑待复核。
校验同时识别方向词——"下跌 5.81%"对应真值 −5.81% 判为通过，"上涨 5.81%"则判为方向相反。

**⑤ 人工值不得触发机械论点。**
`--overrides` 只允许覆盖非判定字段，且必须携带来源。判定引擎依赖的字段一旦出现在覆盖文件中，
系统会直接中止而不是静默忽略。这样既给私有数据和人工核查留入口，又不破坏“论点由机器真值触发”的边界。

## 数据来源与口径

主数据源为 **iFinD（同花顺）**，akshare 作免费补充。字段分三类：

- **直接取**：PB、ROE、净利同比、股息率、资金流等
- **需加工**：历史分位、年化波动率、板块聚合、解禁压力、盈利多期趋势等
- **只能人工补**：海外公司业绩、渗透率、产业测算等研报口径数据

**ETF 是分析对象，取数按字段性质分两层。** 板块名解析出的分析对象，是
`underlying_map.json` 中该板块唯一映射的可交易 ETF；用户明确点名且已通过代码校验的 ETF
优先于板块名反推结果，并会反向校正板块名，避免“点名酒 ETF、实际分析食品饮料”的口径漂移。

- 行情类字段（波动率、区间涨跌幅、换手率分位、成交额分位）取 ETF 自身价格序列。
- 估值与盈利类字段（PB/PE/ROE/净利同比等）先读取 ETF 的跟踪指数，再取该指数的真实成分股，
  按整体法聚合；不再用 iwencai 按行业名模糊匹配的近似篮子。

若官方成分取不到，系统才退回行业篮子；板块/ETF 口径取数失败时如实报缺口，
不再退回单只代表个股冒充板块。ETF 真实篮子会绕过按板块名建立的旧缓存，防止两种篮子互相污染。

**板块口径采用整体法。** `板块PB = Σ市值 / Σ净资产`，而非各成分股 PB 的算术平均，
也非市值加权平均。ETF 场景使用跟踪指数真实成分；没有可用 ETF 时，才使用板块前 N 大成熟成分股
（剔次新）的行业篮子。早期用单只代表股代表整个板块导致分红和估值失真，现已禁止该回退。

**事件由具体公司引发时，独立获取该公司自身数据。** 触发实体（如"SK海力士业绩发布"中的
SK海力士）与代表标的、挂钩标的是三个不同角色：触发实体是事件的当事公司本身，即使是
境外标的，系统也会尝试单独取其价格与估值数据，与 A 股板块数据严格分池，避免报告
通篇分析板块却从未提及事件当事方本身。

**同业对比自动推断，不依赖人工维护清单。** 按 iFinD 行业层级查找兄弟板块
（"电子-半导体-集成电路制造"对应同层的封测 / 设计 / 设备 / 材料），同层样本过少则自动升一级。
跨大类比较 PE 无意义——半导体 126 倍与证券 13.9 倍之间推不出"证券便宜"。

**静态数据缓存复用。** 行业分类、指数成分、历史序列这类当日不变的数据取一次存本地，
将调用配额留给真正时变的数据。

## 人工介入节点

系统不是全自动黑箱，有五个人工节点：

1. **选题确认**——辅路径下候选主题由人工勾选，不自动生成
2. **论点勾选**（`--pick`，可选）——选取哪几条论点组成正文主轴由分析师决定，
   系统只负责将选中的组织成文。不加则由系统按"尽量跨类别"自动选取
3. **研报原文核对**——`--pick` 模式下选用研报观点前，分析师核对逐字原文、页码与出处
4. **人工补数**（可选）——从内部底稿复制覆盖模板，填写私有数据或外部事实及其来源，
   再以 `--overrides` 重跑；人工值只进入写作，不进入机械判定
5. **内部底稿与成品复核**——核对实际数据口径、OptionHelper 调用结果、版面预算和可疑数字

- 板块机会型、事件驱动型端到端跑通，并以真实数据反复验证

  同等地位的机器验证论点
- 分析对象为板块唯一映射或用户点名的可交易 ETF；行情类字段取 ETF 自身，
  估值/盈利类字段取其跟踪指数真实成分股整体法结果
- 事件由具体公司引发时，独立获取该公司自身行情与估值数据
- 研报文档通道：PDF → 观点候选，逐字原文 + 机械校验
- 人工勾选正文主轴论点（`--pick`）
- 人工补数文件（`--overrides`），带来源留痕且禁止覆盖机械判定字段
- PDF 导出与一页通正式交付硬校验（`--pdf`；超页不得正式交付）
- 挂钩标的择优已接入；板块没有确定映射时才运行多维候选比较
- 候选择优会同时比较候选自身的年化实现波动率与历史分位；ETF 的波动率不以代表个股替代
- 最新版 OptionHelper Skill Quote 桥接（`--optionhelper quote`）：消费正式冻结事实并在页底生成参考报价表
- 情景收益带：按固定的“近20日收益分位 × 近20日实现波动率分位”筛选历史相似状态，
  展示其后约1个月/3个月收益的 P25/中位/P75；仅作历史条件分布，非预测、非产品建议
- PySide6 桌面界面（`python gui/start.py`）：输入、事件证据表单、进度、结果、运行记录与高级补数入口
- 高风险市场/行业确认闸门：港股、跨市场、产业链和多行业主题必须由分析师确认；白名单外
  ETF/指数经真实性、暴露与流动性校验后仅作本次临时标的

**尚未完成**

- Word 导出
- GUI 的报价队列仅驻留本次桌面会话，不支持跨会话恢复；这是为了不持久化尚未执行的产品选择
- exe 打包
- OptionHelper 仍是外部依赖：需要明确选择独立 Python、通过统一就绪检查、在项目 memory
  保存 iFinD Refresh Token；Recommender 通过本项目当前配置的 LLM 充当其 AgentPort，失败不会阻断主流程
- GUI 已直接订阅 run_id 对应的结构化日志，支持串行正式报价队列、取消未启动任务及强制重新审核后的安全重试
- 超页后不会自动删改正文、图表或冻结报价；系统会阻止正式交付并给出压缩方向，分析师复核修改后需重新导出实测

**已知短板**

- 判定覆盖不均：资金/筹码 17 条已接 15 条、盈利/基本面 15 条已接 11 条，
  而供需产业格局（17 条）与扩散映射（9 条）判定为 0，这两类暂不参与自动触发。
  它们恰是产业逻辑最集中的部分，是报告视角仍显单薄的根因。目前经研报文档通道部分补足。
- 宏观类论点是市场级的，换标的判定不变。系统会限制单份报告中此类论点最多入选 1 条，
  避免挤占真正体现标的差异化的角度，但不做默认排除——由分析师用 `--pick` 判断取舍。
- 产业趋势型报告所需的产业口径数据（渗透率、中外产能对比、前瞻 PE）几乎全靠人工补充，
  自动化程度显著低于板块机会型。
- 触发阈值多为实测拍定的经验值，仍需按实际研报口径校准。
- 研报表格数列的自动抽取尚不稳定，图表主要仍来自行情数据。
- OptionHelper 对含每日观察日程的产品（如双边鲨鱼鳍）目前可能在定价前被交易日日历绑定校验
  拦截：历史数据覆盖边界与交易日历首尾交易日未完全一致时即拒绝继续。这是日期覆盖元数据
  的一致性问题，不等同于行情缺失；不需要每日观察的普通结构不受该校验影响。长期应由
  OptionHelper 将覆盖区间规范到实际首末交易日，或校验交易日集合完整包含；当前集成层不改写
  OptionHelper，只记录失败并改选不依赖每日观察的已核验候选。

## 配置

密钥存于 `config.local.json`（不进版本库），或通过环境变量提供。

```json
{
  "DEEPSEEK_API_KEY": "...",
  "IFIND_ACCOUNT": "...",
  "IFIND_PASSWORD": "...",
  "OPTIONHELPER_SKILL_ROOT": "C:/Users/你的用户名/Desktop/option-helper_3/option-helper",
  "OPTIONHELPER_PYTHON": "C:/明确选择的环境/python.exe"
}
```

前三项用于研报助手主流程。后两项只在使用 `--optionhelper quote` 时需要：

- `OPTIONHELPER_SKILL_ROOT` 指向最新版 Skill 根目录；当前机器会自动发现桌面
  `option-helper_3/option-helper`，换机时应显式配置。
- `OPTIONHELPER_PYTHON` 不设默认值，必须先明确选择。桥接层每次正式调用前都会用同一个
  绝对路径执行 Skill 的 `environment_check.py --check-readiness`；确认后的路径可保存在
  被 Git 忽略的 `.optionhelper/interpreter.txt`，后续运行自动复用。
- 正式入口会把本项目的 `.optionhelper/runtime`、`data`、`result` 分别注入为新版 Skill
  的三个外部 Store；不会写入桌面的 Skill 安装目录，也不会沿用旧版嵌套 Store。
- iFinD Refresh Token 不再放入 `config.local.json` 或环境变量。按 Skill 流程明确确认后，
  使用 `environment_check.py --save-ifind-refresh-token --project-root <本项目目录>` 交互保存到
  `.optionhelper/memory.md`；该目录已被 `.gitignore` 排除。
- 默认从一次性 `.optionhelper/selection.pending.json` 读取 Agent 交接；报价后会进入
  `.optionhelper/selections/archive/<run_id>.json`。如需更换 pending 文件位置，可配置
  `OPTIONHELPER_SELECTION_PATH`。受控 Host 部署则配置 `OPTIONHELPER_HOST_URL`。

LLM 使用 DeepSeek，默认模型 `deepseek-v4-flash`，可在 GUI 的“LLM 设置”中切换模型和 API Key，
也可用 `DEEPSEEK_MODEL` 环境变量覆盖；
新版 OptionHelper 不复用该模型网关，也不会由桥接层启动第二个模型服务。环境变量优先于
`config.local.json`。

> **当前网络限制：** 主研究链路的 DeepSeek 请求会通过 `core.config.no_proxy()` 强制直连
> `https://api.deepseek.com`，不会使用系统/VPN/Clash 代理。若本机无法直连该 API 的 443 端口，
> 运行会在“解析需求”阶段失败，iFinD 尚未被调用；网页版 DeepSeek 可对话并不能证明 API 可达。
> “直连 / 系统代理 / 自定义兼容 API 地址”的可配置网络模式尚未实现，需先使用可直连该 API 的网络。

密钥不打包进 exe——可被反编译提取。分发时各人填写自己的密钥；
若需大范围推广，走公司内网后端代理，统一充值、限流与审计。

### 更换 iFinD 账号

完整更换 iFinD 账号时，需要分别更新两条凭证通道：

- `IFIND_ACCOUNT` 和 `IFIND_PASSWORD`：Research Helper 研究取数所用的 iFinD SDK 登录；
- `IFIND_REFRESH_TOKEN`：仅供 OptionHelper 在正式报价时换取短期访问令牌，不能替代前者。

桌面端可在“数据与报价凭证 → iFinD 凭证…”中一次输入。既有密码和 Token 不会回显，
留空表示保持原值；账号密码保存至被 Git 忽略的 `config.local.json`，Refresh Token 仍由
OptionHelper 原子保存至被忽略的 `.optionhelper/memory.md`。若 Windows 环境变量中已设置
`IFIND_ACCOUNT` 或 `IFIND_PASSWORD`，环境变量优先，应同时更新或移除旧值。
